Notebooks

A notebook is two things: a page that is saved and a memory that is not

The page

Cells of code and text, and under each code cell the output of the last time it ran. This is the file, analysis.ipynb. It is what you send to a colleague.

The kernel

A running Python that holds every name any cell has bound since it started. It lives on your laptop only, and ends when you close it.

What goes wrong. The page and the kernel can disagree, and nothing on the screen says so. Every problem of this session is one form of that sentence.

Day 1's model again: names bound to objects. In a script the names start empty on every run. In a notebook they persist between cells, in whatever order you ran them, and that is both the charm and the trap.

Hidden state, first form

A deleted cell leaves its names behind in the kernel

known = set(district_of)
if row["meter_id"] not in known:
    continue
  • For Salma the notebook works: her kernel still holds known
  • For anyone else, and for her after a restart: NameError: name 'known' is not defined
  • The file she sent does not contain the code that produced its own outputs

The sentence "it works on my machine" has a precise meaning here: it works in my kernel. Deleting a cell removes text from the page; it does not undo what the cell did.

Hidden state, second form

An output can be older, or newer, than the code printed above it

factor = 3.0
anomalies = [...]   # above factor * median
print(len(anomalies), "anomalies")
# 27 anomalies
27
on the page, under "factor = 3.0"
18
on a clean run from top to bottom
What happened. A cell further down set factor = 2.0, and the anomaly cell was run again afterwards. The 27 is true of a factor nobody can see beside it.

Both numbers are from the lab's notebook: 27 anomalies at factor 2.0, 18 at 3.0. Nine extra visits by a maintenance crew, from a number that looked reproducible. Nobody did anything unreasonable: trying a what-if and scrolling back up is how notebooks are used.

The one habit

Restart and run all, then read the numbers

  • Restart empties the kernel: every name is gone
  • Run all runs the page in the order a reader sees it
  • If it stops, the page depended on something it does not hold
  • If a number changes, the old one was stale
  • Then save: counts 1, 2, 3 and on tell the next reader it was done

And one rule of writing

Set each name in one cell. A second question gets a second name: strict_factor, not factor again. Then no cell can change what an earlier cell means.

In JupyterLab: Kernel, Restart Kernel and Run All Cells. Before any number leaves a notebook for a report, a slide or a message, this is the check. It costs the running time of the notebook, which is also a useful thing to know.

Where code lives

Three homes for code, each good at one thing

Notebook

For looking: a question asked once, steps you want to see, results and notes on one page. State persists between cells.

Script

For repeating: the same steps on new files, by anyone, with one command. Starts empty every run.

Module

For sharing: functions that other code imports, written once and tested in one place. Runs nothing by itself.

They work together. A notebook that imports a tested module is a good notebook. Tomorrow's capstone is a script on top of modules.

This is the second course outcome: say which home fits a task, with a reason. None of the three is the grown-up one. The mistake is using one for another's job: a monthly report run by hand from a notebook, or a one-off question wrapped in a package.

One file, two uses

Importing a file runs its top level. So the top level should only define things.

def build_report(path):
    ...

def main():
    print(build_report("readings.csv"))

if __name__ == "__main__":
    main()
  • python report_tool.py: the file is the program, __name__ is "__main__", and main() runs
  • import report_tool: the same lines run, __name__ is "report_tool", and nothing is called
  • So a test can import build_report without starting the tool

Lab 1.2 used this line without much comment; this is its explanation. Without the guard, importing the file for a test would read the month file and print a report.

A package as a program

An entry point is the one door through which the tool is started

miqyas/
  __init__.py
  __main__.py     the door
  cli.py          arguments and main()
  readings.py     load and validate
  anomalies.py    the rule
  report.py       aggregate and render
from miqyas.cli import main

raise SystemExit(main())
  • python -m miqyas runs __main__.py
  • main() returns a number, and SystemExit hands it to the system as the exit code

Two short files that look like ceremony. They are what makes "one command" true: the person on duty needs to know the name of the package and nothing about its inside.

argparse

Arguments replace the file names typed into cells

report.add_argument("--readings", type=Path, required=True,
                    help="the readings file (CSV)")
report.add_argument("--factor", type=float, default=3.0,
                    help="anomaly threshold, times the median")

Converted

type= turns the text of the command line into a path or a float, or refuses it with a message.

Required or default

An input is required. A setting has a default that is written down once.

Documented

--help is built from these calls: the usage text cannot drift from the code.

Show "python -m miqyas report --help" from the reference package if there is a terminal on screen. Type hints did for functions what type= does here for the command line: the conversion and the refusal happen at the edge.

Speaking to other programs

The exit code is how a tool tells a schedule whether it worked

CodeMeaning in Miqyas
0The report was written
2An input file is missing, or the arguments are wrong
1Something unexpected: Python ended with a traceback
  • Zero means success; anything else means "do not use the output"
  • A missing file is expected trouble: one clear line and code 2, not a traceback
  • Rejected rows are not a failure: the report counts them, and the code is still 0

The third bullet is Day 3 carried over: bad records are reported, not fatal. Argparse itself exits with 2 for wrong arguments, which is why the tool uses 2 for a missing input.

Messages

The result goes to the file. What happened on the way goes to the log.

log = logging.getLogger("miqyas")

log.info("%d rows accepted, %d rejected",
         len(readings), len(rejections))
log.error("no such file: %s", path)
  • A level on every message: with -v you see the steps, without it only problems
  • Log messages go to the error stream, so the output of the tool stays clean
  • Counts and file names belong in a log. A customer's phone number or ticket text does not
Personal data. A log is copied, mailed and kept for years. Yesterday's rule holds here: mask before anything is written, printed or logged.

Print was the right tool for three days of learning. In a tool that runs unattended, print mixes the result with the commentary and cannot be turned down. The check of lab 4.2 looks for print calls in the package.

Reproducibility

Same files in, same bytes out: a property you can test

  • No time of the run in the report: the time goes in the log
  • A fixed order everywhere: sorted districts, anomalies by meter and day
  • The encoding and the line ends are named when writing
  • Nothing remembered between runs: no kernel, no default that grows
python -m miqyas report ... --out a.md
python -m miqyas report ... --out b.md
# then compare the bytes of a.md and b.md
Why it matters. When the report changes next month, you know the input changed, or the code did. Without this property you know nothing.

This is the evidence of the sixth course outcome: one command, two runs, the same report. Defect A of yesterday broke exactly this, through a default argument that remembered the first run.

Checkpoint

The test run prints a report. Why?

A colleague's file monthly.py defines three functions and ends with the line main(). A test file starts with from monthly import clean. Running the tests reads the month file and prints the whole report before any test starts.

pytest calls every function it finds in an imported file
Importing runs the file's top level, and the call of main() is at the top level
Importing clean also imports main, and imported functions run once
The file has no __main__.py beside it
Why. An import runs every top-level line. Put the call under if __name__ == "__main__": and the file can be both imported and run.

Answer: the second. The third option is the common half-belief: that "from x import y" loads only y.

The modules are supplied and sound; the participants write three arguments, the two-line __main__.py and the body of main. The first run of "python -m miqyas" fails with "No module named miqyas.__main__": let them read it. The check compares the report byte for byte with the reference, so the file must be written with newline set, and it wants exit code 2 without a traceback for a missing file, 27 anomalies at factor 2, no print and a clean strict type check. Typical problems: write_text without newline on Windows; args.factor not passed on; main without a return value.

Tests

A test is an example with a verdict

>>> is_anomaly(5.0, [1.0, 1.0, 1.0])
True
def test_far_above_is_an_anomaly():
    assert is_anomaly(5.0, [1.0, 1.0, 1.0]) is True
  • You have run examples at the prompt all week and judged the answers by eye
  • A test keeps the example and the expected answer, so a machine can judge it again
  • uv run pytest finds the functions named test_, runs each, and reports the ones whose assert was false

The supplied tests of every lab since Day 1 were this. Today the participants write them. Nothing new in the language: a function and an assert.

The shape of a test

Arrange, act, assert: three parts, one reason to fail

def test_exactly_three_times_is_not_an_anomaly():
    history = [1.0, 1.0, 1.0]             # arrange
    result = is_anomaly(3.0, history)     # act
    assert result is False                # assert
  • Arrange an input small enough to check in your head
  • Act with one call of the thing under test
  • Assert one fact about the result
  • The name is the sentence the test proves: it is what a colleague reads when it fails

The history of three ones is deliberate: its median is visible. Yesterday's shrink step and this arrange step are the same skill, which is why a shrunk failing case becomes a regression test almost unchanged.

Choosing examples

Mistakes live at the edges, so that is where the examples go

The boundary

Exactly three times the median, and just above it. > and >= differ at one point only.

Nothing

An empty history. What should happen is a decision; the docstring states it and a test holds it.

Each argument

If changing factor changes no test's answer, no test would notice that it is ignored.

A way to find them. Read the docstring and the signature. Every promise and every argument deserves an example that would fail if it were broken.

Ask the room where the validation of Day 1 had its edges: 0 and 200 cubic metres, the empty cell, the duplicate. The same three kinds. An ordinary case in the middle is worth one test, not five.

An example that discriminates

A good example gives different answers for the right rule and a wrong one

HistoryMedianMean
1, 1, 11.01.0
1, 1, 1, 1, 101.02.8
  • With the first history, a rule built on the mean passes every test you write
  • With the second, the value 3.5 is an anomaly by the median (above 3.0) and not by the mean (below 8.4)
  • One example, chosen so that the two rules disagree

This is the idea the lab's check measures. It swaps the rule for four wrong versions and asks whether any test fails. A test file is judged by the mistakes it would catch, not by how many tests it has.

What a green run means

Passing tests prove the examples, not the program

What you know

On these inputs the code gives these answers, today and after every change, checked in a second.

What you do not know

Anything about inputs nobody thought of. Defect B of yesterday passed every test that used a sorted list.

  • Tests and types catch different mistakes: a type checker never runs the code, a test never sees the lines it does not reach
  • A test that cannot fail is worse than none: it reports safety that is not there

Keep this sober. Tests are the cheapest evidence there is, and they are evidence about examples. The honest sentence in a README is "the tests cover these cases", which the capstone asks for under "what the tool does not check".

This output is what a participant sees if the boundary is treated as an anomaly. Connect it to the six steps: a failing test starts you at step three, the hypothesis.

Checkpoint

Which test would catch it?

Someone "tidies" the rule and writes value >= factor * median(history) where it said >. Which test fails?

The value 5.0 with the history 1, 1, 1 is an anomaly
The value 1.1 with the history 1, 1, 1 is not an anomaly
The value 100.0 with an empty history is not an anomaly
The value 3.0 with the history 1, 1, 1 is not an anomaly
Why. The two rules differ at one point, where the value equals factor times the median. Only an example on that point can tell them apart.

Answer: the fourth. Each wrong option is a perfectly good test, of something else. That is the lesson: three green tests and the change went through.

One test is supplied; five more are asked for. The check runs the tests on the real rule, then on four wrong versions: the boundary counted, no history counted, the mean for the median, the factor ignored. Do not list the four before the first check. Typical problems: a history whose median is not a round number, so that floating point decides the boundary; a symmetric history for the median test; only tests that expect True. Ask those who catch all four at once what a fifth wrong version could be.

Before you paste

What you send to a hosted assistant has left the organisation

  • Code you wrote for a lab: fine. A traceback: read it first, it may quote a record
  • A customer's ticket, phone number or meter history: personal data, not to be sent to a service your organisation has not approved
  • Shrink first. A case built by hand with two invented meters shows the defect and holds nobody's data

In this lab

The tutor sends your question and the source files you name. It refuses anything under data/. The data here is synthetic; the habit is for the day it is not.

The national references are on the course page: the Personal Data Protection Law and SDAIA's guidelines on generative AI. For a utility's analyst the practical rule is short: approved tools only, and no customer records in a prompt. Shrinking, a debugging step, is also the privacy step.
