Opening a file

Three things to say every time you open a text file

with open(path, encoding="utf-8",
          newline="") as file:
    rows = list(csv.DictReader(file))
  • with: the file is closed when the block ends, also when an error happens inside it
  • encoding="utf-8": you decide how bytes become text, not the machine you happen to be on
  • newline="": for CSV, let the csv module handle line ends, so that a line break inside a quoted cell survives
What goes wrong. Leave the encoding out and the same script reads Arabic on one laptop and crashes on the next. Session 2 shows it.

The forty-line script of Day 1 used open and close by hand. From today every open is a with. The newline argument is what the csv documentation asks for; say it once and move on.

CSV

A CSV reader hands you text for every cell. Numbers and dates are your job.

>>> row = rows[0]
>>> row
{'meter_id': 'M-0001', 'date': '2026-09-01',
 'consumption_m3': '5.399'}
>>> row["consumption_m3"] * 2
'5.3995.399'
  • csv.DictReader uses the header line as keys: one dict[str, str] per row
  • CSV has no types. '5.399' is five characters until you call float
  • Convert in one place, at the door, and reject there what will not convert

The doubled text is the classic first surprise; a type checker catches the next one, text plus number. The row is the first data row of the month file. "At the door" is Miqyas's parse_row: text in, a typed Reading or a rejection out.

JSON Lines

JSON Lines is one JSON value per line: a file you can read one record at a time

with open(path, encoding="utf-8") as file:
    for line in file:
        ticket = json.loads(line)
  • Each line stands alone: a broken line spoils one record, not the file
  • Records can be appended, and streamed with a generator
  • Unlike CSV, a value has a type: text, number, true or false, null, list, object

At Manahil

Each of the 400 tickets is one line with ten fields. The free text is Arabic, English or both in one sentence.

JSON Lines is also the usual format for logs, for model inputs and outputs and for evaluation sets, which is why the tracks ahead use it everywhere. json.loads returns "anything": a dictionary if the line is an object, and a list or a number if it is not; session 3 checks for that.

Writing

Write output that is the same bytes on every run, and that a person can read

with open(path, "w", encoding="utf-8",
          newline="\n") as file:
    json.dump(summary, file,
              ensure_ascii=False, indent=2)
    file.write("\n")
  • ensure_ascii=False: Arabic is written as Arabic, not as ا escapes
  • indent=2: one field per line, so that two versions can be compared
  • Keys in a fixed order: build the dictionary from sorted names
  • No clock time inside the file: put that in the log
Same input, same bytes. Then "did anything change?" is answered by comparing two files, and Day 4's tool can prove it reruns.

Reproducibility is one criterion of the capstone rubric. The enemies are all on this slide: unordered sets, the current time, platform line ends, platform encodings.

Bytes and text

A file holds bytes. Text appears only when an encoding is applied.

The word عداد (meter)Bytes
in UTF-8d8 b9 d8 af d8 a7 d8 af
in Windows-1256da cf c7 cf
  • Text (str) is a sequence of characters: 4 here
  • Bytes are numbers from 0 to 255: 8 here, or 4
  • An encoding is the table between the two. encode goes to bytes, decode comes back
The bytes do not say which table wrote them. Someone has to tell you, or you have to find out.

At a prompt: "عداد".encode("utf-8").hex(" ") and the same with "cp1256"; the outputs are the two rows of the table. len of the text is 4, of the UTF-8 bytes 8.

UTF-8

UTF-8 covers every script and is the encoding to write, always

One byte

English letters, digits, punctuation: the same bytes as ASCII. M-0042 is six bytes.

Two bytes

Each Arabic letter. The letter ف is d9 81.

Not every byte order is valid

A decoder can tell when bytes are not UTF-8. That is a feature: wrong input fails loudly.

  • Older systems wrote one byte per Arabic letter (Windows-1256). Their files are still arriving
  • Read what you are given, with the encoding it was written in. Write UTF-8

Keep the history to one line. The practical point is the third card: UTF-8 detects a wrong file, the one-byte encodings mostly cannot, which the mojibake slide shows.

The trap

open(path) without an encoding uses whatever the machine prefers

with open(path) as file:        # which encoding?
    return [json.loads(line) for line in file]
  • On many Windows laptops the default is a one-byte Western table (cp1252)
  • On most servers and in notebooks in the cloud it is UTF-8
  • So the same script works in one place and fails in the other, on the same file
This is changing. PEP 686 makes UTF-8 the default from Python 3.15. Until every machine you meet runs it, and for every file that is not UTF-8, name the encoding.

The lab's first script names the laptop default explicitly, cp1252, so that every participant sees the same failure whatever their system. Sources: PEP 686, "Make UTF-8 mode default", which lists Python 3.15 as its version.

Reading the error

A decode error names the codec, the byte and the position. Use all three.

UnicodeDecodeError: 'charmap' codec can't decode byte 0x81 in position 131:
    character maps to <undefined>

The codec

"charmap": a one-byte table was decoding. Nobody chose it; it was the default.

The byte

0x81 has no character in that table. In UTF-8 it is the second half of ف.

The position

Byte 131 of what was being decoded: where to look in the file.

Bad input

A program can meet a bad record in three ways. Only one is acceptable.

Crash

Line 37 is broken, so nobody gets the other 434. And tomorrow, line 52.

Pass silently

Skip it, or fill in a default. The report looks complete and is wrong by an unknown amount.

Reject with a reason

The run finishes, the good records are used, and each bad one is listed with where and why.

The rule of the house. Accepted plus rejected equals the lines of the input. Always, and checked by the program itself.

Ask for an example of the middle card from the room's own experience: a total that was quietly missing a branch, a month. Silent loss is the expensive one because nobody goes looking.

Exceptions

An exception travels up the call stack until some caller catches it

parse_value("N/A")raises ValueError
↓
parse_row(row)no handler: passes it on
↓
load_readings(path)has try and except: handles it, goes on
  • raise stops the function at once; nothing is returned
  • Each caller in turn either handles it or is stopped too
  • If nobody handles it, the program ends and prints the stack: the traceback
  • So the place that detects a problem need not be the place that decides what to do

Day 1's call-stack picture, with an error moving through it. The last bullet is the design idea: parse_value knows the text is not a number; only the loop knows that the right response is to record the row and continue.

Catching

Catch the exception you expect, by name. A wide net catches your own mistakes too.

try:
    value = flaot(text)
except Exception:
    skipped += 1
try:
    value = float(text)
except ValueError:
    skipped += 1
  • Left: the misspelt flaot raises a NameError on every row. The net catches it, and the script reports that all 17,690 rows were "skipped"
  • Right: only "this text is not a number" is handled. Anything else still stops the run and shows you where
A bare except: is the widest net of all. The labs' checks refuse it.

Let the room find the typo on the left before you say it. The lesson is not style: a wide except converts programming errors into wrong data, which is the silent failure of the first slide.

Your own exception

An exception of your own can carry what the handler needs: a code and a detail

class Rejected(Exception):
    def __init__(self, reason, detail):
        super().__init__(f"{reason}: {detail}")
        self.reason = reason
        self.detail = detail

raise Rejected("BAD_PRIORITY",
               f"priority is {value!r}")
  • A reason code for programs: it can be counted, grouped and tested
  • A detail for people: the actual value, so that someone can repair the line
  • The handler catches Rejected and nothing else: every other exception is a bug to see

Six lines of class are all the object-oriented programming this session needs: a kind of exception with two extra fields. !r shows the value with its quotes, which makes an empty text or a stray space visible in the log.

Validation as guards

Day 1's guard clauses, with raise in place of return

if ticket["priority"] not in PRIORITIES:
    raise Rejected("BAD_PRIORITY", ...)
try:
    date.fromisoformat(ticket["opened"])
except ValueError:
    raise Rejected("BAD_DATE", ...) from None
return ticket
  • The function now returns only good tickets. A caller cannot forget to look at a reason
  • Let the library judge: fromisoformat knows that September has 30 days
  • Translate its ValueError into your own exception, with your own code
  • The first guard that fires wins: one reason per line

On Day 1 validate_reading returned a reason text and "" for a good row; every caller had to remember to test it. Raising makes the good path the only path. "from None" keeps the traceback short; mention it only if asked.

The loop

The try wraps one call for one line, and the loop goes on

for line_no, line in enumerate(file, start=1):
    try:
        accepted.append(parse_ticket(line))
    except Rejected as problem:
        rejected.append((line_no,
                         problem.reason,
                         problem.detail))
  • Inside the loop: one bad line costs one line
  • A try around the whole loop would end at the first rejection and lose every line after it
  • The line number is counted here, where it is known, and stored with the reason
You wrote this shape an hour ago. Decode each line, catch the decode error, collect the failure: the same loop with another exception.

A method, not a talent

Six steps turn "it gives wrong numbers" into a fix that stays fixed

1 · Reproduce

One command that shows the wrong result, every time.

2 · Shrink

The smallest input that still shows it.

3 · Hypothesis

One sentence: "I think … because …".

4 · Test it

An observation that would prove you wrong.

5 · Fix

The smallest change, at the cause.

6 · Regression check

A test that fails without the fix.

Write the six words on the board and leave them there for the lab. The order matters most where people skip: changing code before step 3, and stopping after step 5. The debugging log of the lab has one heading per step.

Steps 3 and 4

Say what you think is wrong before you touch the code, then try to prove yourself wrong

A hypothesis

"I think the count is wrong because line 40 of report.py starts the total at 1." A file, a line, a reason.

A test of it

"If so, a file of one row gives 2." Run it. One row gives 1: the hypothesis is dead, in thirty seconds, with no code changed.

Step 6

A regression test fails on the defect and passes on the fix. Then it stays.

def test_total_of_one_row():
    rows = [{"consumption_m3": "0.5"}]
    assert total(rows) == 0.5
  • Write it from the shrunk case, before or right after the fix
  • See it fail on the old code. A test you never saw fail may be testing nothing
  • See it pass on the new code
  • Keep it: it runs with every later change, for as long as the code lives
The lab's check does step 2 of that list for you. It puts each defect back into a copy of the package and expects your test to fail there.

The example test belongs to the invented hypothesis of the slide before. pytest is introduced properly tomorrow; today a test is a function whose name starts with test_ and that asserts something. "Fixed" without a test means "fixed until someone tidies this function".

Day 3 · wrap-up

Three things to keep

Name the encoding

Bytes become text through a table you choose. Decode strictly, report what fails, never ignore.

Every line is accounted for

Reject with a code and a detail; catch only what you expect; accepted plus rejected equals the input.

Six steps

Reproduce, shrink, hypothesis, test, fix, regression check. The test is what makes the fix last.
