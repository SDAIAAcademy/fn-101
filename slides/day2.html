Review of Day 1

One list or two?

A function clean(rows) runs rows.sort() and returns rows[:10]. A caller writes top = clean(month). Afterwards, what is true of month?

It is unchanged: the function worked on its own copy
It is sorted, and still has all its rows
It is sorted and cut to ten rows
It is the same object as top
Why. sort() mutates the caller's list; the slice makes a new one. A function that returns a result and also changes its argument surprises every caller.

Answer: sorted, all rows. Use it to restate the rule for today: functions over collections return new collections and leave their arguments alone, unless the name says otherwise. sorted(rows)[:10] would have been the polite version.

Dictionaries

A dictionary answers "what belongs to this key?" in one step

district_of = {
    "M-0001": "Al-Rabwa",
    "M-0002": "Al-Yasmin",
}
print(district_of["M-0002"])
print("M-9001" in district_of)
  • Each key appears once and leads to one value
  • Looking up a key does not search: it goes straight there
  • in asks whether a key exists, without raising an error
  • Keys keep the order in which they were added
Think "index", like the back of a book. You do not read the book to find a word; you look the word up.

The two prints: Al-Yasmin and False. Everything in this session is one of three uses of this structure: an index (key to record), a counter (key to number), a grouping (key to list).

Pattern 1

Counting: one pass, one dictionary, get with a default

counts: dict[str, int] = {}
for reading in readings:
    meter_id = reading["meter_id"]
    counts[meter_id] = counts.get(meter_id, 0) + 1
  • counts.get(key, 0): the count so far, or 0 for a key not seen yet
  • counts[key] += 1 alone raises KeyError on the first reading of a meter
  • collections.Counter(…) is this loop, ready made

On the month

588 meters have readings in the clean file; M-0001 has 30, one per day of September (lab 2.1).

Pattern 2

Grouping: the value is a list, and each record joins the list of its key

by_meter: dict[str, list[float]] = {}
for reading in readings:
    value = float(reading["consumption_m3"])
    meter_id = reading["meter_id"]
    by_meter.setdefault(meter_id, []).append(value)
  • setdefault(key, []) returns the list of the key, creating an empty one the first time
  • After the loop, by_meter["M-0042"] is that meter's whole month
  • This is how Miqyas finds each meter's median before it looks for anomalies
What goes wrong. dict.fromkeys(ids, []) gives every key the same list. Yesterday's aliasing, in a dictionary.

The warning is a seeded defect of a later lab; plant the idea and move on. Counting and grouping are the two halves of every "per something" question a manager asks.

Why one step

The key itself says where its value is stored

  • Python turns the key into a number, its hash, and uses it as an address
  • So finding a key costs about the same in 600 entries as in 600,000
  • The price: a key must never change. Text, numbers and tuples can be keys; lists and dictionaries cannot
>>> {["M-0001", "2026-09-01"]: 0.7}
TypeError: unhashable type: 'list'
>>> {("M-0001", "2026-09-01"): 0.7}
{('M-0001', '2026-09-01'): 0.7}

One idea only: the address comes from the key, so the key must be immutable. No hash tables on the board. The tuple key returns in session 2 for repeated readings and in the stretch of lab 2.4.

Sets

A set holds each value once and answers "is it in there?" in one step

known = {m["meter_id"] for m in meters}
print(len(known))             # 600
print("M-0042" in known)      # True
print("M-9001" in known)      # False
  • A set is a dictionary with keys and no values
  • x in a_list walks the list; x in a_set goes straight to the answer
  • No order, no positions, no repeats: only membership
You have used one already. Yesterday's validate_reading(row, known) took the registry as a set, for exactly this question.

Tie back to lab 1.4: if row["meter_id"] not in known. With a list of 600 ids that line would be the nested loop of session 1 in disguise.

What the two differences mean

The same operator, two different problems, two different owners

Registered, and not one row in September. A dead meter, an empty house, a reader that never synchronised. A question for the field team.

5 ids are unknown

M-9001 to M-9005, four rows each. A registry that is behind, or a mistyped id. A problem in the data, and those 20 rows cannot be billed to anyone.

What a set gives up

A set drops repeats and forgets order: sort before you show it

>>> ids = ["M-0002", "M-0001", "M-0002"]
>>> set(ids)
{'M-0002', 'M-0001'}
>>> sorted(set(ids))
['M-0001', 'M-0002']
  • set(a_list) is the shortest way to drop repeats
  • The order you see printed is not promised, and can differ between runs
  • sorted(…) turns any collection into a list in a fixed order
A report must be the same on two runs. Anything that leaves your function for a file or a screen goes through sorted first.

The order of text in a set changes between runs of Python on purpose. This is the first appearance of the week's reproducibility rule: same input, same bytes out. Lab 2.2's functions return sorted lists for this reason.

Pattern

Finding repeats: remember what you have seen, as a set of tuples

seen: set[tuple[str, str]] = set()
repeated: set[tuple[str, str]] = set()
for reading in readings:
    key = (reading["meter_id"], reading["date"])
    if key in seen:
        repeated.add(key)
    seen.add(key)
  • The identity of a reading is the pair: this meter, this date
  • A tuple cannot change, so it can be a member of a set
  • set() makes an empty set; {} is an empty dictionary

Comprehensions

A comprehension builds a collection in one expression: what, from where, which

values = [float(r["consumption_m3"]) for r in rows]                 # a list
high = [v for v in values if v > 5.0]                               # with a filter
known = {m["meter_id"] for m in meters}                             # a set
district_of = {m["meter_id"]: m["district"] for m in meters}        # a dictionary

What

The expression at the front: one item of the result.

From where

for … in …: the same line as in a loop.

Which

An optional if at the end keeps only some.

They have read three of these already today. Read each aloud in the order "for each r in rows, give me float of…". The brackets decide the type of the result.

Judgement

One expression and one condition fit a comprehension; anything more wants a loop

Comprehension

Transform each item, or keep some. The reader sees the whole idea on one line.

Loop

Counting and grouping, a try around each item, two results at once, an early exit, or a line that no longer fits on the screen.

ok = [float(r["consumption_m3"]) for r in rows if r["consumption_m3"].strip() != ""
      and r["meter_id"] in known and 0 <= float(r["consumption_m3"]) <= 200]
What goes wrong. The line above converts twice, crashes on N/A, and cannot say why a row was left out.

The rule of thumb is not about style: validation needs a reason per rejected row, and a comprehension has no place to put one. That is why yesterday's validation function was a function.

Generators

A function with yield hands over one value, then waits to be asked again

def read_values(path):
    with open(path, encoding="utf-8",
              newline="") as file:
        for row in csv.DictReader(file):
            yield float(row["consumption_m3"])
  • return ends a function; yield pauses it, with all its names kept
  • The next request resumes it on the line after the yield
  • At any moment, one row exists. The file stays open until the loop is done

Yesterday's call-stack picture helps: the frame of read_values is not thrown away at yield, it is set aside and brought back. This is the reference solution of lab 2.3; do not leave it on screen during the lab.

Laziness

Calling a generator function runs nothing: the work happens when values are asked for

callvalues = read_values("data/readings_large.csv") no file is opened yet
next(values)opens the file, reads one row, gives 0.606 and pauses
next(values)reads one more row, gives 0.544 and pauses
sum(values)asks again and again until the file ends: the total of everything left
for and sum ask for you. You rarely write next; every loop over a generator is this conversation.

Demonstration at a prompt in the folder of lab 2.3 after the lab, or with a three-line generator before it: call it, show that nothing printed, then call next twice. The two values are the first two rows of the large file.

The price

A generator can be walked once. Then it is empty.

>>> values = read_values(path)
>>> sum(values)
137769.165
>>> sum(values)
0
>>> len(values)
TypeError: object of type 'generator' has no len()
  • No length, no positions, no second pass
  • Need two results? Compute both in one loop, or call the function again for a fresh generator
  • Need to sort, or to find a median? You need all the values: use a list
The silent zero. A second pass does not raise an error. It quietly gives the result for no data.

The stretch of the lab. The silent zero is a real source of wrong reports: a total of 0 looks like a quiet month. Anomaly detection needs each meter's median, hence all its values: Miqyas loads the month into a list, on purpose.

The short form

Round brackets make a comprehension lazy

total = sum([float(r["consumption_m3"])
             for r in rows])

total = sum(float(r["consumption_m3"])
            for r in rows)
  • First: build a list of 100,000 numbers, add them, throw the list away
  • Second: hand each number to sum as it is made
  • Works with sum, max, min, any, all, sorted, set

The only difference is the square brackets. Good default: when the collection is consumed at once by a function, leave the square brackets out.

Records

A dictionary as a record accepts any mistake until the line that uses it

ticket = json.loads(line)
ticket["priorty"] = "urgent"
if ticket["opened"] < "2026-09-01":
    ...
  • Line 2 misspells the field and adds a new key. No error, ever
  • Line 3 compares dates as text. It works only while every file writes year-month-day
  • Nothing says which fields a ticket has, or what type each is
  • The checker sees dict[str, str] and can help with none of it

Dictionaries are right for "key to value" questions, which was this morning. A ticket is something else: a fixed set of named fields. That is a record, and Python has a tool for it.

Data classes

A data class is a record with named, typed fields, written in six lines

@dataclass(frozen=True)
class Ticket:
    ticket_id: str
    opened: date
    district: str
    priority: str
    status: str
    text: str
  • The decorator writes the constructor, a readable printout and == for you
  • Ticket(ticket_id="T-20001", opened=…) builds one; t.priority reads a field
  • A misspelt field is an AttributeError at run time and an error from the checker before

The fields are the hints of Day 1, now attached to a name. Show at a prompt how a Ticket prints: all fields, by name. The class has no phone field on purpose; the slide after next says why.

Frozen

frozen=True makes a record that nobody can change behind your back

>>> t.priority = "low"
dataclasses.FrozenInstanceError:
    cannot assign to field 'priority'
>>> urgent = replace(t, priority="urgent")
  • Yesterday: a shared mutable object changes for every name that holds it
  • A frozen record can be shared freely: there is nothing to mutate
  • A "change" makes a new record with dataclasses.replace, like upper() on a string
  • Frozen records can be keys of a dictionary and members of a set

The whole of Day 1's aliasing problem disappears for records that cannot change. Miqyas's Reading, Meter, Rejection and Anomaly are all frozen data classes.

Behaviour that belongs to the record

A method is a function that lives with the data it needs

    def age_days(self, today: date) -> int:
        """Whole days from the day the
        ticket was opened to today."""
        return (today - self.opened).days
  • self is the record the method was called on: t.age_days(today)
  • today comes in as a parameter. A method that asked the clock would give a different answer tomorrow, and could not be tested
  • opened is a date, so subtraction gives days. As text it would give an error

Sorting

sorted needs to know what to compare: give it a key function

RANK = {"urgent": 0, "high": 1,
        "normal": 2, "low": 3}

by_text = sorted(tickets,
                 key=lambda t: t.priority)
by_rank = sorted(tickets,
                 key=lambda t: RANK[t.priority])
  • The key function is called once per item; items are ordered by what it returns
  • By text: high, low, normal, urgent. Alphabetical, and useless
  • By rank: urgent first, because 0 is the smallest
  • lambda t: … is a function small enough to write in place

The rank dictionary is this morning's index pattern. sorted returns a new list and leaves tickets alone; drill 2 had the difference between sorted and sort.

Responsible use

A record carries only the fields the task needs

In the file

Ten fields per ticket, among them a phone number and an identity number: personal data.

In Ticket

Six fields. The queue is ordered by priority and age; it needs to call nobody and identify nobody.

  • What is never copied into the record cannot be printed, logged or written by mistake
  • The free text of a ticket can hold a phone number too. Tomorrow's first lab masks it before anything is written

Checkpoint

Which key puts the queue in working order?

Customer care works the most urgent tickets first and, within a priority, the oldest first. RANK gives urgent 0 and low 3. Which call is right?

sorted(waiting, key=lambda t: (t.priority, t.opened))
sorted(waiting, key=lambda t: (RANK[t.priority], t.opened))

Why. The tuple is compared item by item: rank decides, and the date decides only between tickets of the same rank. Smaller comes first, so 0 and the earliest date lead.

Three things to keep

Choose by the question

A dictionary for "what belongs to this key", a set for "is it in there", a list for order. One lookup replaces a loop.

Stream what you use once

A generator keeps memory flat and can be walked once. Sort, median and second passes need a list.

Records have names and types

A frozen data class with only the fields the task needs; a tuple key puts them in order.
