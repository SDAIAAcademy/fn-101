Session 1

Values, names and references

  • Trace a short program line by line with a table of names and objects
  • Predict when two names share one mutable object and when they do not
  • Distinguish rebinding a name from mutating an object
01
Names and objects

A name is a label tied to an object, not a box that holds a value

reading = 0.742
latest = reading
reading = 0.810
print(latest)        # 0.742
  • Line 1 makes an object, 0.742, and ties the name reading to it
  • Line 2 ties a second name to the same object
  • Line 3 ties reading to a new object; latest is not asked
Read = as "now names". The right side is worked out first; then the name on the left is tied to the result.

Draw it: two labels, one object, then move one label. Everything else in this session is this drawing with a list in place of the number. Ask what line 4 prints before you reveal the comment.

Aliasing

Assignment never copies: b = a gives one list two names

a = [1, 2, 3]
b = a
b.append(4)
print(a, len(b))

It prints

[1, 2, 3, 4] 4

There was only ever one list. append changed it, and both names show the change.

What goes wrong. You "save the original" with backup = rows, clean rows, and the backup is cleaned too.

This is snippet 1 of the lab, and its answer is given on the lab page as the model of the form. Ask the room what a is b would print. Two names for one object is called an alias.

Two different things a line can do

A line either changes an object or moves a name. Know which.

The lineWhat it doesWho sees it
b.append(4), b[0] = 9, d["k"] = 1changes the object (mutation)every name tied to that object
b = b + [4], b = [], n = n + 1ties the name to another object (rebinding)only that name
The test. Is there a bare name on the left of =? Then it is rebinding. A dot or a bracket on the left, or a method that changes in place, is mutation.

Spend time here: this table decides snippets 3, 4 and 6. Note for the curious: b += [4] on a list mutates in place, which is why the table avoids it; say so only if asked.

Mutable and immutable

Numbers, strings and tuples cannot change, so sharing them is harmless

Cannot be changed

int, float, str, bool, tuple, None. Every "change" makes a new object: y = y + 5, name.upper().

Can be changed in place

list, dict, set, and most objects you define. Sharing one of these is where surprises come from.

x = 10
y = x
y = y + 5
print(x, y)          # 10 15

Snippet 2 has the same shape as snippet 1 and the opposite result. The difference is not the type of the name, names have no type; it is that line 3 rebinds. With an immutable value rebinding is the only thing a line can do.

Copies

A copy is one level deep: the outside is new, the inside is shared

meter = {"id": "M-0042", "readings": [0.6]}
backup = dict(meter)
backup["id"] = "M-0043"
backup["readings"].append(0.7)
print(meter["id"], meter["readings"])
  • a[:], list(a), dict(d) and .copy() make a new outer object
  • What is inside is not copied: both dictionaries point at one list of readings
  • copy.deepcopy copies all levels, when you need it
It prints M-0042 [0.6, 0.7]: the id was safe, the readings were not.

Draw two dictionaries with their own "id" arrows and one shared list. Records that hold lists are everywhere in data work, so this is the aliasing bug participants will really meet. Do not reveal the callout before the room has voted.

Two questions

== asks "equal value?"; is asks "the same object?"

a = [0.7, 0.9]
b = a
c = a[:]
print(a == c, a is c)    # True False
print(a == b, a is b)    # True True
  • Use == for values, almost always
  • Use is for None: if value is None
  • When a trace surprises you, a is b tells you whether you have one object or two

Keep it short. The one rule to leave: compare with None using is; the type checker session returns to it.

Calling a function

A call ties the parameter name to the caller's object: no copy there either

def add_reading(log, value):
    log.append(value)
    log = []
    log.append(-1)

day = [1.2]
add_reading(day, 0.8)
print(day)
calllog and day name one list
line 2that list becomes [1.2, 0.8]
line 3log is tied to a new empty list
line 4the new list gets -1; nobody else sees it
prints[1.2, 0.8]

Demonstration: in the workspace, uv run trace.py 1.1/snippets/s4.py prints exactly these steps, with "one object, 2 names" where it applies. Show it after the lab's prediction step, not before. The lesson for tomorrow: a function that mutates its argument changes the caller's data.

Checkpoint

What does the last line print?

Salma keeps yesterday's readings before cleaning today's: before = rows, then rows.remove(-1.0), then rows = rows + [0.5]. The list started as [0.7, -1.0]. What is before now?

[0.7, -1.0]
[0.7]
[0.7, 0.5]

Why. remove mutates the one shared list, so before loses the value too. rows + [0.5] makes a new list and ties only rows to it.

Session 2

Functions with clear contracts

  • Split a script into functions that each do one job
  • State a function's inputs and output in its signature and docstring
  • Explain what a function can see and change, using scope and the call stack
02
Decomposition

A forty-line script does four jobs, and you can test none of them

1 · Loadread the file into rows
→
2 · Cleankeep the numbers, count the rest
→
3 · Computethe amount due
→
4 · Presentfour lines of text
  • To check the tariff you must have a file, run everything, and read the last line
  • A function per job gives each job a name, a way in and a way out

The script is monthly_bill.py of lab 1.2: meter M-0042, 27 days billed and 3 skipped, 17.211 cubic metres, 44.95 SAR. The tariff is invented for the course. Ask: the tariff changes; how do you prove the new one is right for exactly 15 cubic metres?

Contracts

Everything in comes through parameters; everything out through return

def bill(total_m3):
    """Take a month's consumption in
    cubic metres; return the amount
    due in SAR."""
    if total_m3 <= 15:
        amount = total_m3 * 2.0
    else:
        amount = 30.0 + (total_m3 - 15) * 4.5
    return amount + 5.0
  • The first line and the docstring are the contract: what goes in, what comes out
  • No name from outside is read, nothing outside is changed
  • So one line checks it: bill(15.0) == 35.0
What goes wrong. A function that prints its result returns None. The caller has nothing to work with.

The three values the lab's tests use: bill(0.0) is 5.0, bill(15.0) is 35.0, bill(20.0) is 57.5. Print against return is the most common beginner confusion: show x = print(3) then print(x) if the room hesitates.

Where the effects go

Keep files and printing at the edge, and the middle becomes easy to test

Edge in

load_rows(path) is the only function that opens a file.

The middle

clean, bill, format_bill: values in, values out. The same input always gives the same output.

Edge out

main() is the only place that prints.

You will see this shape all week. Miqyas loads at one end, writes a report at the other, and everything between is functions you can call with three rows typed by hand.

Do not use the word "pure" as jargon; "same input, same output, touches nothing else" is enough. Three of the four functions of the lab can be tested without any file on disk: that is the first question of the lab's "check yourself".

Scope

A name bound inside a function lives inside that call, and nowhere else

total = 0

def add(value):
    total = value
    return total

add(5)
print(total, add(7))     # 0 7
  • Assigning to total inside add makes a local name
  • The total of line 1 is a different name in a different scope
  • A function may read an outer name; assigning never reaches it
So do not rely on outer names at all. Pass what the function needs; return what it produces.

Snippet 5. There is a global statement; mention it only to say the course never needs it. The useful consequence: a function cannot quietly change your variables by assignment. It can change your lists by mutation, as snippet 4 showed.

The call stack

Every call gets its own frame of names, stacked on the caller's

bill(17.211)total_m3, amount
↓
main()rows, values, skipped
↓
the moduleload_rows, clean, bill, main
  • The top frame is the function running now
  • When it returns, its frame and its local names are gone
  • A traceback is this stack printed at the moment of an error, the top frame last

The stack is read from the bottom of the slide up: the module called main, main called bill. Tie it forward: on Day 3 they read tracebacks from the last line upward, which is this picture. A debugger's "step into" and "step out" move along it.

Saying the contract

A docstring states the contract; a doctest is an example that runs

def parse_value(text):
    """Turn the consumption cell into
    cubic metres.

    >>> parse_value(" 0.750 ")
    0.75
    >>> parse_value("12")
    12.0
    """
  • First line: what goes in, what comes out, in words
  • Lines that start with >>> are a session someone can retype
  • python -m doctest file.py runs them and reports any that no longer hold
Examples age well. A sentence can drift from the code without anyone noticing; an example that runs cannot.

This function is from Miqyas, the tool they meet on Day 3. Doctests are for a few telling examples; the full tests live in test files, which is Day 4. The stretch of lab 1.2 adds one doctest.

Run or import

The main guard lets a file be both a script and something to import

def main():
    rows = load_rows("data/sample_meter.csv")
    values, skipped = clean(rows)
    amount = bill(sum(values))
    ...

if __name__ == "__main__":
    main()
  • Run the file: Python sets __name__ to "__main__", so main() runs
  • Import the file: __name__ is "monthly_bill", nothing runs
  • The tests import it. Without the guard, every test run would print a bill

The lab's check imports the file and expects no output. This two-line idiom is the seed of Day 4, session 2, where the script becomes a command with arguments.

A trap in the signature

A default value is made once, when the function is defined

def tag(reading, tags=[]):
    tags.append(reading)
    return tags

first = tag("high")
second = tag("low")
print(first, second, first is second)

It prints

['high', 'low'] ['high', 'low'] True

def tag(reading, tags=None):
    if tags is None:
        tags = []
One list for every call. A mutable default remembers what earlier calls did. Remember this slide on Day 3.

Snippet 8. It is aliasing again: the default object is shared by all calls that do not pass their own. One of the seeded defects of the Day 3 debugging lab is exactly this, in a function that loads readings; do not say which.

Session 3

Type hints and a checker

  • Annotate parameters and return values with built-in types
  • Read a type checker's report and find the line it points at
  • Handle a value that may be None before using it
03
Type hints

A type hint is a promise about a value, written where a tool can check it

def parse_value(text: str) -> float | None:
    if text == "":
        return None
    return float(text)
  • text: str: callers promise to pass text
  • -> float | None: the function promises a number, or None
  • Python itself ignores hints when it runs the code
  • A type checker reads them and finds every line that breaks a promise

The contract of session 2, made precise enough for a machine. Stress the third bullet: parse_value(3) still runs and still crashes; hints are for the checker and for the reader.

Hints for collections

Say what is inside: a list of what, a dictionary from what to what

HintReads asAt Manahil
list[float]a list of numbersone meter's month
dict[str, int]text keys, whole-number valuesreadings per district
set[str]a set of textthe known meter ids
tuple[str, str, float]exactly three values, in this ordermeter, day, cubic metres
dict[str, str]text to textone row of a CSV file
The last row matters. A CSV reader gives you text for every cell, numbers included. The hint says so, and the checker stops you adding text to a number.

These are the built-in names, lower case, no import needed on any Python the course supports. Tomorrow's collections session uses these same five shapes.

The value that is not there

"Or None" in a hint forces every caller to handle the missing case

value = parse_value(text)
return meter_id, day, round(value, 3)
value = parse_value(text)
if value is None:
    return None
return meter_id, day, round(value, 3)
  • Before: an empty cell crashes at round(None, 3), some day, on some file
  • After the check, the checker knows value is a float on the last line: this is called narrowing
Not if not value. A reading of 0.0 is a real reading, and it is "not value" too.

The warning is a real bug in utility data: empty houses read zero. is None asks the question you mean. Most of the nine errors of the lab are this one pattern in different places.

Reading the report

Every line of the report is a place, a complaint and a code

parser.py:26: error: "None" object is not iterable  [misc]
parser.py:43: error: Unsupported operand types for > ("float" and "str")  [operator]
parser.py:45: error: Incompatible return value type (got "str", expected "float | None")  [return-value]

Line 26

Three names are unpacked from something that may be None.

Line 43

A number is compared with text. Python would raise a TypeError here.

Line 45

The function returns text where its hint promised a number.

Three of the nine messages of the lab, copied from the run. Method: start at the top, open the line, ask "which promise does this line break?", fix, run again. One fix often removes several messages. The code in brackets is what you search the documentation for.

What hints cannot do

A checker verifies your code, not the file someone sends you

The checker catches

Text added to a number, a forgotten None, a wrong return, a misspelt field of a record: mistakes in the program.

The checker cannot see

A cell that holds N/A, a reading of 9,000 cubic metres, a meter that is not in the registry: mistakes in the data.

Both are needed. Hints keep the code honest. Validation at the door, with a reason for every rejected row, keeps the data honest. That is Day 3.

Prevent the false comfort: "it type-checks" says nothing about whether row 12,440 holds a number. The lab of session 4 builds the first validation function; Day 3 makes it report reasons.

Session 4

Parsons problems

  • Order the lines of a function so that each name is bound before it is used
  • Use indentation to say which lines belong to a branch, a loop or a try
  • Reject a distractor by saying what it would do
04
Parsons problems

All the lines are given, scrambled. You decide order and indentation.

return total
if value >= 0:
total = value
def total_valid(values):
total += value
for value in values:
total = 0.0
  • No syntax to recall: every character you need is on the page
  • What is left is the structure: what runs first, what is inside what
  • One line is a distractor: it looks right and does not belong
Why practise this. It is the skill between reading and writing, and it is one part of the supervised check.

This is the warm-up of lab 1.4. Let the room solve it aloud: someone names the first line, the next person the second. The distractor is total = value: ask what the function would return for [1.5, 2.5] with it (2.5, the last value).

Rule 1

A line can run only after the lines that bind the names it reads

text = row[…].strip()needs row, a parameter
→
value = float(text)needs text
→
if value < 0 or value > 200:needs value
  • For each line, list the names it reads; find the line that binds each
  • That gives you chains like this one before you think about meaning at all
  • Run a line too early and Python says NameError: name 'value' is not defined

It is session 1 again: names are bound by assignment, by def, by parameters, by for. A NameError in the lab means an order mistake, and the message names the name.

Rule 2

Indentation says what belongs to what, and one level changes the answer

for value in values:
    if value >= 0:
        total += value
return total
for value in values:
    if value >= 0:
        total += value
    return total
  • Left: return after the loop, the sum of all valid values
  • Right: return inside the loop, so the function ends after the first value
  • Both are valid Python. Only a test, or a trace, tells them apart

For [1.5, -2.0, 0.0, 2.5] the left version returns 4.0 and the right one 1.5. The lab's warm-up test uses exactly this list. Ask: what does the right version return for an empty list? (None: the loop body never runs and the function falls off the end.)

The shape of a validation function

Reject each bad case early; what reaches the last line is good

def validate_reading(row, known):
    text = row["consumption_m3"].strip()
    if text == "":
        return "MISSING_VALUE"
    ...
    if row["meter_id"] not in known:
        return "UNKNOWN_METER"
    return ""
  • Each if guards one return with one reason
  • The order of the guards is part of the specification
  • The final line is not indented under any if
Pair them up. In a scrambled validation function, match every if with its return first. Half the puzzle is done.

The four reasons of the lab, in order: MISSING_VALUE, NOT_A_NUMBER, OUT_OF_RANGE, UNKNOWN_METER. They are four of the six reason codes Miqyas reports; the month file holds 40, 15, 18 and 20 rows of them. On Day 3 the returns become exceptions with a reason.

Where the try goes

try wraps the one line that can fail; except names that failure

try:
    value = float(text)
except ValueError:
    return "NOT_A_NUMBER"
  • float("N/A") raises ValueError
  • except TypeError: would catch nothing here: the error passes through and the function crashes
  • except: alone would catch everything, including your own typing mistakes
Name the exception you expect. You find its name by trying the failing call once and reading the last line of what Python prints.

Demonstration: at a Python prompt type float("N/A") and read "ValueError: could not convert string to float: 'N/A'". Then float("0,742"): also ValueError; the month file has 7 values written with a decimal comma. Exceptions get a whole session on Day 3.

Checkpoint

Where does the last line of the function go?

A function counts the good rows. Placed so far: count = 0, the for line, the if line, count += 1. Left: return count. A test shows it returns 1 for 30 good rows.

Directly under count = 0, before the loop
Under count += 1, at the same depth
Under the if line, at the depth of the if
After the loop, at the depth of the for line
Why. A result that depends on every row is returned once, after the loop. A return of 1 for 30 good rows says the return sits inside the loop.

Answer: the last option. The scenario describes the bug of the second option: ask which wrong position produces exactly 1 for 30 good rows, and which produces 0 or 1 depending on the first row (the third).
